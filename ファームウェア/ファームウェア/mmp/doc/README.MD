# はじめに
最終更新日：2026年08月11日

---
#### このファームウェアとは
**「通信経路の違いを完全に吸収し、  
すべての制御を '文字列コマンド' に統一した、  
拡張性と教育性に優れたマルチモジュール制御ファームウェア」**


---
## 1. 全体アーキテクチャ概要
- 複数の通信経路を**単一のコマンドパーサ**へ集約し、**統一された処理フロー**でコマンド実行
- **責務を明確に分離**し、各層の役割を一貫させた設計
- 通信経路固有の処理は、**早い段階で吸収**  
- コマンドパーサ以降は**通信経路を意識しない**設計  
- 各機能モジュールは機能単位で独立しており、**高い保守性**を持つ


---
## ２. 特徴
### 🔹**マルチ通信・マルチユーザに対応**
- 全通信経路(シリアル/TCP/HTTP)を同時に扱える  
- ユーザごとに独立したユーザ認証・接続管理がある
- 各機能モジュールは、ユーザーごとのデータを独立して扱える(アクセスIDで識別)

### 🔹**機能モジュールの構造が単純で新規追加が容易**
- 各機能は独立したソースファイルとして実装
- 共通処理は基底クラス・パーサが担当、機能モジュールは固有の処理に集中できる

### 🔹**通信経路を意識しない共通コマンド文法**
Python / Arduino / .NET からの命令は、URI形式の同じ文法で統一  
**`send("ANALOG/IN!")` のように文字列を送るだけ**。

内部でのクライアントID割当、IPスロット管理などはすべてファームウェアが担当。

### 🔹**拡張性の高さ**
- ひな形・共通関数が豊富で、新しい通信経路(LoRa/Bluetoothなど)の追加が容易  
- 利用制限(同時接続数・認証ユーザ数)の変更も定数変更のみでＯＫ
- 機能モジュールの追加は、ほぼ純粋な機能部分だけの開発でＯＫ

## ３. ユーザ認証・接続認証

### ● 通信経路別のユーザ認証
| 経路       | ID     | ユーザ認証   |接続認証|
|------------|--------|--------------|----------|
| シリアル   | 0～1   | 認証なし     |なし ※物理接続の為|
| TCPブリッジ| 2〜11  | 最大10ユーザ |あり ※TCP接続別に識別|
| Web-API    | 12〜21 | 最大10ユーザ |なし ※リクエスト単位で完結の為 |

### ● 特徴
- 動的に IP を登録するので、複数デバイスの同時接続に強い  
- 任意の経路から同一コマンド体系を実行可能  
- 経路数増加（LoRa、BLE など）にも拡張しやすい

## ４. 全体の流れ
### (概要)
1. **経路別処理(通信アダプタ)**：認証したのちに、リクエスト内容を取り出しコマンドパーサへ
1. **コマンドパーサ**：リクエスト内容を該当の機能モジュールへ
1. **機能モジュール**：リクエスト内容の機能を実行し、処理結果を仮想ストリーム `StringStream` に出力
1. **コマンドパーサ**：仮想ストリームに蓄積された処理結果を取得し、通信アダプタへ返す
1. **経路別処理(通信アダプタ)**：実行結果を編集し、通信経路に返す

```mermaid
flowchart LR
  subgraph Client["通信経路"]
    S["シリアル"] 
    W1["TCP Bridge"] 
    W2["Web-API"]
  end

  subgraph Firmware["MMP(ファームウェア)"]
    MS["全ポートを処理"] 
    MT["TCP接続のみを処理"] 
    MW["WebServerリスナが処理"] 
    P["コマンドパーサ"]
    M["機能モジュール群"]
  end

  S  <--> MS
  W1 <--> MT
  W2 <--> MW

  MS <--> P
  MT <--> P
  MW <--> P

  P  <--> M
```

### (詳細１)

リクエストは、責務別のモジュールを経て処理されます。
```mermaid
flowchart LR
    A["通信経路<br/>Serial/TCP/HTTP"] 
    B["通信アダプタ(adp*.h)<br/>経路固有の事情を吸収"]
    C["コマンドパーサ(parser.h)<br/>コマンドをルーティング"]
    D["ModuleBase(mod.h)<br/>機能モジュールの共通I/F"]
    E["機能モジュール(mod*.h)<br/>INFO,ANALOG,DIGITAL<br/>PWM,I2C,MP3"]

    A --> B
    B -->|"統一された<br/>コマンド形式"| C
    C -->|"owns() / handle()"| D
    D --> E

    E -->|"統一された実行結果"| C
    C -->|"統一された<br/>実行結果"| B
    B --> A
```

### (詳細２)
各レイヤで共有する実行コンテキストや共通資源は、MmpContext を介して受け渡します。<br>
通信アダプタが受け取る処理結果は、実際には共通資源(MmpContext)経由で取得します。
```mermaid
flowchart LR
    A["通信経路<br/>Serial/TCP/HTTP"]
    B["通信アダプタ(adp*.h)<br/>通信経路の違いを吸収"]
    C["<b>共通資源<br/>（MmpContext）<b/>"]
    D["コマンドパーサ(parser.h)<br/>コマンドをルーティング"]
    E["機能モジュール(mod*.h)<br/>INFO,ANALOG,DIGITAL<br/>PWM,I2C,MP3"]

    A <--> B
    B -->|"共通形式"| D
    B <-->|"仮想ストリーム，コマンドパス，アクセスID，処理結果"| C
    C <--> D
    D -->|"コマンド実行"| E
    E <--> C
```

## ５. 機能モジュールとの連携
各機能モジュールは ModuleBase を継承し、以下の特徴を持ちます。
- **コマンド所有判定 (`owns()`) と処理本体 (`handle()`) の明確な分離**
- 出力は **仮想ストリーム(MmpContext内)** へ統一  
- モジュール追加/削除が非常に簡単
